# PacePact — CLAUDE.md

## What We're Building

PacePact is a social training platform for groups of friends preparing for the same endurance event (marathon, triathlon, cycling sportive, etc.). It generates an AI-powered training plan for the group based on the event date and training ambition, then automatically marks sessions complete by consuming Strava webhook events. A shared leaderboard keeps everyone accountable.

MVP is fully free — no payments, no plans. Get users in, get the core loop working, then monetise later.

## Core Concepts

### Group
A group is built around a single event. It has:
- An event name, type, and date
- A training ambition: `finish` | `podium` | `pb` (personal best)
- A generated training plan (array of weekly sessions)
- Members (users who have joined and connected Strava)
- A leaderboard (points per member, updated in real time)

A user can belong to many groups simultaneously. Each group has its own training plan and leaderboard.

### Training Plan
Generated once at group creation via Claude API. The plan is a structured JSON array of sessions across the weeks from today until race day. Sessions have a type (run, ride, swim, brick, rest), a target (distance, duration, or effort), and a week number.

The ambition level (`finish` / `pb` / `podium`) shapes the plan's intensity — volume, interval work, and recovery balance.

The plan is stored in Supabase and is the source of truth for what constitutes a "completed session" when a Strava activity arrives.

### Strava Integration
Each user connects their Strava account via OAuth. PacePact stores their Strava access token and refresh token in Supabase.

PacePact registers a single Strava webhook endpoint. When any connected user completes an activity, Strava POSTs to that endpoint. PacePact then:
1. Identifies which user the activity belongs to
2. Fetches the activity details from Strava
3. Matches it against their pending sessions in all active groups
4. Marks matching sessions complete and awards points
5. Triggers a Supabase Realtime broadcast to update leaderboards live

### Points
Points are simple and transparent:
- Completing any scheduled session: **10 points**
- Bonus for completing a session early in the week: **+2 points**
- Bonus for a session that exceeds the target (e.g. ran further than prescribed): **+3 points**
- Streak bonus (7 consecutive days with at least one session): **+5 points**

Points are stored per user per group so leaderboards are group-scoped.

## Database Schema

### `users`
Managed by Supabase Auth. Extended with a `profiles` table.

```sql
profiles (
  id uuid references auth.users primary key,
  display_name text,
  avatar_url text,
  strava_athlete_id bigint unique,
  strava_access_token text,
  strava_refresh_token text,
  strava_token_expires_at timestamptz,
  created_at timestamptz default now()
)
```

### `groups`
```sql
groups (
  id uuid primary key default gen_random_uuid(),
  name text not null,
  event_name text not null,
  event_type text not null, -- 'marathon' | 'half_marathon' | 'triathlon' | 'cycling' | 'obstacle' | 'custom'
  event_date date not null,
  ambition text not null, -- 'finish' | 'pb' | 'podium'
  training_plan jsonb not null, -- generated by Claude, array of sessions
  invite_code text unique not null,
  created_by uuid references profiles(id),
  created_at timestamptz default now()
)
```

### `group_members`
```sql
group_members (
  id uuid primary key default gen_random_uuid(),
  group_id uuid references groups(id) on delete cascade,
  user_id uuid references profiles(id) on delete cascade,
  points integer default 0,
  joined_at timestamptz default now(),
  unique(group_id, user_id)
)
```

### `sessions`
One row per planned training session, per user, per group.

```sql
sessions (
  id uuid primary key default gen_random_uuid(),
  group_id uuid references groups(id) on delete cascade,
  user_id uuid references profiles(id) on delete cascade,
  week_number integer not null,
  session_type text not null, -- 'run' | 'ride' | 'swim' | 'brick' | 'rest'
  target_distance_km numeric,
  target_duration_minutes integer,
  target_description text,
  scheduled_date date,
  completed boolean default false,
  completed_at timestamptz,
  strava_activity_id bigint,
  points_awarded integer default 0,
  created_at timestamptz default now()
)
```

### `strava_webhook_events`
Raw log of incoming Strava webhook payloads for debugging and replay.

```sql
strava_webhook_events (
  id uuid primary key default gen_random_uuid(),
  payload jsonb not null,
  processed boolean default false,
  processed_at timestamptz,
  created_at timestamptz default now()
)
```

## Key Implementation Details

### Group Creation Flow

The group creation is a multi-step form:

1. **Event details** — event name, type (dropdown), event date
2. **Training ambition** — single choice: `Just finish`, `Beat my PB`, `Go for podium`
3. **Review + generate** — shows a summary, user clicks "Generate Training Plan"

On submit, the API route calls Claude to generate the plan, stores the group and sessions in Supabase, then redirects to the group page.

### Claude Plan Generation (`lib/claude/generate-plan.ts`)

```typescript
const systemPrompt = `You are an expert endurance sports coach. 
You generate structured training plans as JSON. 
Respond ONLY with valid JSON — no markdown, no explanation.`

const userPrompt = `
Generate a training plan for the following:

Event type: ${eventType}
Event date: ${eventDate}
Weeks until event: ${weeksUntil}
Training ambition: ${ambition} (finish = comfortable completion, pb = beat personal best, podium = competitive)

Return a JSON array of sessions. Each session:
{
  "week_number": number,          // 1 = first week
  "session_type": string,         // "run" | "ride" | "swim" | "brick" | "rest"
  "target_distance_km": number | null,
  "target_duration_minutes": number | null,
  "target_description": string,   // human-readable e.g. "Easy 5km recovery run"
  "day_of_week": number           // 1=Mon, 7=Sun — suggested day
}

Rules:
- Include a rest day each week
- Taper in the final 2 weeks
- Scale intensity to ambition: finish = low volume, pb = moderate with intervals, podium = high volume with structured speed work
- For triathlon include swim, ride, run, and brick sessions each week
- For marathon/half focus on run volume with one long run per week
- Maximum ${weeksUntil * 6} sessions total
`
```

Parse the response, validate the structure, then fan out sessions per group member into the `sessions` table.

### Strava Webhook (`app/api/strava/webhook/route.ts`)

The webhook endpoint handles two things:

**GET** — Strava's subscription verification challenge. Respond with the `hub.challenge` value.

**POST** — Incoming activity event. Flow:
1. Verify the request signature using `STRAVA_WEBHOOK_SECRET`
2. Log raw payload to `strava_webhook_events`
3. If `object_type !== 'activity'` or `aspect_type !== 'create'`, return 200 and stop
4. Look up the user by `owner_id` (Strava athlete ID) in `profiles`
5. Fetch full activity from Strava API (need distance, type, elapsed time)
6. Pass activity to `activity-matcher.ts`
7. Award points, mark sessions complete
8. Broadcast via Supabase Realtime

Always return HTTP 200 immediately — Strava will retry on non-200.

### Activity Matching (`lib/strava/activity-matcher.ts`)

Matching an incoming Strava activity to a planned session:

1. Find all incomplete sessions for this user across all active groups where the scheduled date is within ±2 days of the activity date
2. Filter by activity type match (Strava `Run` → session type `run`, etc.)
3. If `target_distance_km` is set, the activity distance must be ≥ 85% of target to count as complete
4. If `target_duration_minutes` is set, elapsed time must be ≥ 85% of target
5. Match to the closest session. If no match found, the activity is ignored (user may have done an unscheduled workout — that's fine, no points)

### Leaderboard Realtime

The `LeaderboardTable` component subscribes to Supabase Realtime on the `group_members` table filtered by `group_id`. When a Strava webhook awards points and updates `group_members.points`, the leaderboard updates live for all members currently viewing the group page.

```typescript
const channel = supabase
  .channel(`leaderboard:${groupId}`)
  .on('postgres_changes', {
    event: 'UPDATE',
    schema: 'public',
    table: 'group_members',
    filter: `group_id=eq.${groupId}`
  }, (payload) => {
    // update local state
  })
  .subscribe()
```

### Strava OAuth Flow

1. User clicks "Connect Strava" on their profile page
2. Redirect to Strava OAuth with scopes: `activity:read_all`
3. Strava redirects to `/api/strava/callback?code=...`
4. Exchange code for access + refresh tokens
5. Store tokens on `profiles`, store `strava_athlete_id`
6. Redirect back to profile with success state

Token refresh: before any Strava API call, check `strava_token_expires_at`. If expired, call the refresh endpoint and update Supabase before proceeding.

## Invite System

Each group gets a unique `invite_code` (nanoid, 8 chars) at creation. The group creator shares a link: `https://pacepact.com/join/[inviteCode]`.

The `/join/[inviteCode]` page:
- If not logged in → prompt to sign up, then redirect back after auth
- If logged in but Strava not connected → prompt to connect Strava first
- If all good → add to `group_members`, redirect to group page

## Strava Webhook Registration

Strava requires you to register your webhook endpoint before events start flowing. This is a one-time setup done via Strava's API:

```bash
curl -X POST https://www.strava.com/api/v3/push_subscriptions \
  -F client_id=YOUR_CLIENT_ID \
  -F client_secret=YOUR_CLIENT_SECRET \
  -F callback_url=https://pacepact.com/api/strava/webhook \
  -F verify_token=YOUR_WEBHOOK_VERIFY_TOKEN
```

Do this after deploying to Railway. The webhook URL must be publicly accessible — local development requires a tunnel (ngrok or similar) for testing.

## Development Notes

- Use Supabase RLS (Row Level Security) from day one. Users should only be able to read groups they are members of
- The `sessions` table will grow fast — index on `(user_id, group_id, completed, scheduled_date)`
- Strava API rate limits: 100 requests per 15 minutes, 1000 per day. The webhook approach avoids polling so this is unlikely to be a problem in early stage
- Plan generation via Claude takes 5–15 seconds — show a loading state on the group creation form and don't let the user navigate away
- Store the raw Claude response alongside the parsed plan in the `groups` table (`training_plan_raw text`) for debugging bad parses
